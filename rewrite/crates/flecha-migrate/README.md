# Saved profile migration

`migrate_profile(user_data_dir, profile_name, destination)` reads the shipping Flecha shell's `chrome.storage.local` and the selected Chromium profile's cookies and web storage on Linux and macOS. Supply absolute paths with no symlink components, an explicit profile name such as `Default`, and a new destination under a trusted, existing parent outside the source. Keep the shipping browser closed until the call returns. Windows uses a [different process singleton](https://chromium.googlesource.com/chromium/src/+/158.0.8127.2/chrome/browser/process_singleton_win.cc) and is outside this implementation.

The LevelDB lives in `<profile>/Local Extension Settings/abdiaepfgbbhdjaecjipmaailijaaide`. The shell [pins that ID](../../../chromium/patches/0004-flecha-shell-extension-id.patch) to its manifest key. Chromium stores each value as JSON. The value for `state` is itself a JSON string. [Chromium LevelDB value store](https://chromium.googlesource.com/chromium/src/+/158.0.8127.2/components/value_store/leveldb_value_store.cc)

- The migrator opens the source directory by directory without following symlinks. It refuses live local locks, remote locks and ambiguous locks. It accepts a local lock for a PID that no longer exists. It reads the `SingletonLock` link as text and never removes it. [Chromium POSIX singleton](https://chromium.googlesource.com/chromium/src/+/158.0.8127.2/chrome/browser/process_singleton_posix.cc)
- Only regular LevelDB data files are copied. The migrator checks file and directory metadata and checks the singleton again after the copy. It validates `CURRENT`, journal framing and checksums, and table footer bounds and metadata checksums before opening the private copy. C++ LevelDB 1.23 verifies data blocks, and the migrator checks its iterator status before publishing. Any detected corruption aborts migration. The destination is published with a single rename that refuses to replace an existing path. [Native binding 1.0.1 (MIT)](https://github.com/christian-smith/cruzbit-leveldb-sys/blob/master/Cargo.toml), [bundled LevelDB and Snappy versions](https://github.com/christian-smith/cruzbit-leveldb-sys/blob/master/build.rs)
- `session/state.json` uses the rewrite's normal `StateStore`, including typed settings and ad-block exceptions. A damaged primary falls back to `state:last-good`. When the primary key is missing or neither snapshot is readable, the rewrite starts fresh. Valid last-good and before-import snapshots are converted to the rewrite's backup slots. Invalid entries, `state:damaged` and unknown keys are counted and left in the source. [Shipping recovery rules](../../../chromium/shared/savedState.ts)
- `legacy-boosts.json` and `legacy-boosts-compiled.json` contain the original JSON maps when present. The Boosts unit can read them without reopening the old profile. The migrator never runs their contents. [Shipping Boosts storage](../../../chromium/shell/features/boosts.ts)
- `cef/Default` receives `Cookies` and its WAL and SHM files when present, plus local storage, session storage, IndexedDB and WebStorage. The migrator also accepts cookies under the source profile's `Network` directory. `cef/Local State` receives only the `os_crypt` object when present. New rewrite profiles open `cef/Default`. Existing rewrite profiles with `cef/shared` keep using their existing shared context.

`cargo test --locked -p flecha-migrate` exercises the public API with generated temporary LevelDBs and [fixtures written by C++ LevelDB](tests/fixtures/leveldb/README.md). The tests take SHA-256 hashes of file contents and record paths and symlink targets before and after migration. They pass explicit fixture paths without discovering installed profiles. The isolated CI step runs from a workspace containing just this crate, `flecha-core` and `flecha-services`. The native dependency builds bundled LevelDB and Snappy using CMake and a C++ compiler.

## Chromium files and CEF 158

The shipping fork is [Chromium 158.0.8127.2](../../../chromium/CHROMIUM_VERSION). The rewrite pins [CEF 158.0.3, Chromium 158.0.8127.18](../../pins.toml). The Chromium tags are on the same branch. The five upstream storage implementations below had identical file hashes across the tags. That establishes format compatibility at those implementations. Portability still depends on which destination profile and services use them, and on OS encryption. CEF maps its request-context cache paths to Chromium profiles. The migrator copies the selected profile's default storage partition. Chromium storage partitions for isolated Spaces require their own mapping to rewrite contexts. [CEF build pin](https://github.com/chromiumembedded/cef/blob/8c29be2/CHROMIUM_BUILD_COMPATIBILITY.txt), [CEF profile binding](https://github.com/chromiumembedded/cef/blob/8c29be2/libcef/browser/chrome/chrome_browser_context.cc), [rewrite profile setup](../flecha-cef/src/runtime.rs), [shipping storage partitions](../../../chromium/patches/0034-spaces-with-separate-cookies.patch)

| File | On-disk format | Could it move as-is? |
| --- | --- | --- |
| `Network/Cookies` | SQLite schema 24, minimum compatible 24 | The schema matches. Encrypted values still need the source key. The global and per-Space cookie stores also need to map to their corresponding CEF contexts. [Cookie store](https://chromium.googlesource.com/chromium/src/+/158.0.8127.18/net/extras/sqlite/sqlite_persistent_cookie_store.cc) |
| `Login Data` | SQLite schema 43, minimum compatible 40 | The schema matches. Password values still need the source key and a functioning password store in the destination. [Login database](https://chromium.googlesource.com/chromium/src/+/158.0.8127.18/components/password_manager/core/browser/password_store/login_database.cc) |
| `History` | SQLite schema 70, minimum compatible 16 | A consistent SQLite snapshot is a candidate if the destination uses Chromium's history service for that profile. The SQLite snapshot must include any outstanding WAL transactions. [History database](https://chromium.googlesource.com/chromium/src/+/158.0.8127.18/components/history/core/browser/history_database.cc), [SQLite WAL](https://sqlite.org/wal.html) |
| `Bookmarks` | JSON codec version 1 | The file is a candidate if the destination loads it through Chromium's bookmark model. The rewrite's pinned tabs and folders are separate shell state. [Bookmark codec](https://chromium.googlesource.com/chromium/src/+/158.0.8127.18/components/bookmarks/browser/bookmark_codec.cc) |
| `Preferences` | JSON, with registered preferences and tracked values | Copy selected compatible preferences through their owning services. A wholesale copy assumes the same registry, protected settings and integrity data, including `Secure Preferences` where used. [JSON pref store](https://chromium.googlesource.com/chromium/src/+/158.0.8127.18/components/prefs/json_pref_store.cc), [profile pref factory](https://chromium.googlesource.com/chromium/src/+/158.0.8127.18/chrome/browser/prefs/chrome_pref_service_factory.cc) |

OSCrypt can derive its key from Keychain on macOS and from Secret Service or KWallet on Linux. Access and application identity matter even on the same machine. On Windows the DPAPI key comes from `Local State`. App-Bound encryption can additionally bind it to the application and system. Copying `Cookies` or `Login Data` alone does not establish that CEF can decrypt their contents. [macOS Keychain](https://chromium.googlesource.com/chromium/src/+/158.0.8127.18/components/os_crypt/common/keychain_password_mac.mm), [Linux key provider](https://chromium.googlesource.com/chromium/src/+/158.0.8127.18/components/os_crypt/async/browser/freedesktop_secret_key_provider.cc), [Windows DPAPI](https://chromium.googlesource.com/chromium/src/+/158.0.8127.18/components/os_crypt/async/browser/dpapi_key_provider.cc), [Windows App-Bound encryption](https://chromium.googlesource.com/chromium/src/+/158.0.8127.18/chrome/browser/os_crypt/app_bound_encryption_win.cc)

Desktop launches let CEF select its OS keyring. The isolated launcher keeps the basic password store. Access to the shipping browser's OS keys remains unverified.
