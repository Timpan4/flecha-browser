## Test boundary

The scope is the engine choice in the [rewrite plan](../../../docs/cef-gpui-rewrite-plan.md) and [decision brief](../../../docs/cef-gpui-astra-review-20261123.md). The C++ probe links directly to the same CEF C ABI used by cef-rs. It verifies the CEF commit at startup and creates genuine Alloy windowless browser hosts. It also creates a Chrome-style native-window control. It uses software `OnPaint` to prove that the popup can supply pixels for composition. GPUI rendering, sizing, input, placement and focus were outside this probe. No product files changed.

Run from `rewrite/` with Node.js 24 or newer, `/usr/bin/bsdtar`, and the Linux runtime staged by [prepare.sh](../gpui-cef-compositor/prepare.sh):

```sh
bash spikes/cef-osr-extensions/run.sh
```

[run.sh](run.sh) builds with GCC 16.2.1, C++20 and `-Wall -Wextra -Werror`. The [isolated launcher](../../tools/isolated-run.sh) owns Xvfb, the private D-Bus, the network namespace and process cleanup. The server, debugging connections and policy downloads use that namespace's loopback. All profiles are throwaway directories under the worktree. The run uses the SHA-1-verified Linux beta archive for CEF `158.0.3+g8c29be2` and Chromium `158.0.8127.18`, with Node 24.22.1. [Pins](../../pins.toml) · [CEF compatibility pin](https://github.com/chromiumembedded/cef/blob/8c29be2/CHROMIUM_BUILD_COMPATIBILITY.txt#L9)

[Recorded JSON Lines](evidence.jsonl) contains the final run. Match the `check` field to the cases named below. All 12 probe processes and the harness exited with code 0. The runner enforces a 10-second CDP step and graceful shutdown allowance, and fails on missing expected results. Case names can be passed to `run.sh`. The runner includes each requested preseed's source case automatically. [run.mjs](run.mjs) drives the checks. The [MV3 manifest](extension/manifest.json) declares a `document_start` content script on loopback. The script sets a DOM marker, writes a pathname to storage and asks the worker to read and echo it with the sender's tab ID and incognito flag. The popup reads the install event's storage marker, sends its own message and loads the icon. This measures execution and IPC separately from visual appearance. The no-extension control had no marker, worker or preference record.

| Case in evidence | First document | After install or revisit | Why |

**Startup order is a real failure mode for a fresh install.** The held policy response gives a controlled before/after run in the same Alloy browser. Start the first matching navigation after install and script readiness, or reload a page that finished before installation. A launch switch with the extension available locally and the packed preseed both injected into the first document. The direct source path is `ExtensionService::Init` → registry → `UserScriptManager::OnExtensionLoaded` → asynchronous file load and renderer update. The navigation throttle can defer matching requests when it knows about pending scripts. A profile-initialization callback or a CDP install reply is distinct from the script loader's completion. A source build that needs a deterministic readiness signal should publish the existing completion, rather than add a fixed delay. **Alloy has the extension WebContents helpers.** Chromium attaches the universal observer when the WebContents is created. CEF then calls `AttachHelpers` before initial navigation and constructs `AlloyTabInterface`. Its `TabFeatures::Init` attaches `extensions::TabHelper`, whose constructor uses the extension observer and installs the script executor and action runner. The content script's real sender tab ID and worker reply corroborate that path. The evidence gives no reason to add a second observer or to patch tab-helper attachment. **The earlier Dark Reader failures remain unresolved.** Spike 0 measured whether the rendered page turned dark. It kept the appearance logs but lacked registry state, worker state and a direct content-execution marker from a failing profile. A reload reportedly did not help in that earlier batch, so the proven fresh-install timing case does not explain those failures by itself. The new controls show that a known registered packed extension can work from the first navigation and that copied files can exist without a registered extension. To resolve the old failure, capture the installed entry and worker and instrument actual Dark Reader script execution before interpreting appearance. **CDP and persistence.** The CEF in-process controller calls `DevToolsAgentHost::GetOrCreateFor(inspected_contents_)`. Chromium permits loading on a browser target. The remote socket and pipe supply that target. In the pinned handler, `loadUnpacked`, `getExtensions` and `uninstall` select the last loaded original profile through the default-context manager. The PDL has no explicit request-context parameter. CDP writes the `INSTALLED_VIA_CDP` flag, and startup deletes those records. The switch is also temporary, but its ignored record can remain in Preferences. A legacy MV2 background-page fixture was rejected at load through the browser endpoint (see `legacy/load`). Every successful route in the table exercised the MV3 background service worker. **Policy.** On Linux set `CefSettings.chrome_policy_id` to an absolute policy directory and put `ExtensionInstallForcelist: ["<id>;<update-url>"]` in `managed/*.json`. The CEF setting documentation describes Chrome style, but the pinned startup code sets the policy identifier before browser creation. The Linux provider loaded the policy in a process hosting only Alloy OSR. The fixture used a valid signed CRX3 and local update XML. During fresh CRX installs stderr printed `*** stack smashing detected ***: terminated` eight times without process IDs. Both persistent profiles still installed the CRX and the browser exited cleanly. The emitting process and cause are unverified. Enterprise force-install implicitly grants permissions and prevents user removal while the policy applies. A production install flow needs its own permission review and lifecycle. Store-hosted updates and policy on macOS and Windows are unverified. ## Popup and actions

**A GPUI popover can use a separate OSR browser for a known extension page.** The probe opened `chrome-extension://<id>/popup.html` in the same context and received the fixture's color in a `PET_VIEW` buffer from the CEF browser ID assigned to that popup URL. Its script read the regular profile's storage, reached the worker and fetched a packaged icon. Chromium treated it as a normal Alloy tab, with its own sender tab ID. It did not inherit a toolbar popup's active-tab relationship or gesture grant. `tabs.query` enumerates `BrowserWindowInterface` and its tab lists. Alloy's implementation returns a null browser window. In the Chrome control a popup URL opened as an ordinary window sees that new window's own active tab. [Popup fixture](extension/popup.js) · [TabsQueryFunction](https://chromium.googlesource.com/chromium/src/+/refs/tags/158.0.8127.18/chrome/browser/extensions/api/tabs/tabs_api.cc#599) · [Alloy window contract](https://github.com/chromiumembedded/cef/blob/8c29be2/libcef/browser/alloy/alloy_tab_interface.h#L59-L68) · [Related CEF #4255](https://github.com/chromiumembedded/cef/issues/4255)

**`Extensions.triggerAction` exists on the pin.** An Alloy page target got `Action can only be triggered on a tab target.` Its actual tab target got `Tab target is not attached to a browser window.` The Chrome-style tab returned CDP success for the fixture's action with a declared popup. The handler resolves a Chrome window, its `ExtensionsContainer` and toolbar action model. For a real user click Chromium's action runner grants eligible temporary permissions and either requests the tab-specific popup or dispatches `onClicked` when the action has no popup. Opening the extension URL directly skips those steps. No public CEF extension-handler API supplies an equivalent callback. [CDP action](https://chromium.googlesource.com/chromium/src/+/refs/tags/158.0.8127.18/chrome/browser/devtools/protocol/extensions_handler.cc#165) · [Action runner](https://chromium.googlesource.com/chromium/src/+/refs/tags/158.0.8127.18/chrome/browser/extensions/extension_action_runner.cc#95) · [CEF #3685](https://github.com/chromiumembedded/cef/issues/3685)

**Inventory and icons.** `Extensions.getExtensions` returned ID, name, version, enabled state and path for unpacked installs. The packed policy install was absent from that response even after its worker appeared. The pinned handler filters for unpacked locations and omits icons. After shutdown, `Default/Preferences` and `space/Preferences` held `extensions.settings` records. The runner resolved the absolute unpacked path or the packed path under `<profile>/Extensions/`, then read icon metadata from the saved manifest or the extension's manifest file. The command-line seed retained an entry for an extension the runtime had not loaded, which makes Preferences useful for offline import and lookup. Use the extension registry for live inventory. [CDP inventory filter](https://chromium.googlesource.com/chromium/src/+/refs/tags/158.0.8127.18/chrome/browser/devtools/protocol/extensions_handler.cc#266) · [Preference name](https://chromium.googlesource.com/chromium/src/+/refs/tags/158.0.8127.18/extensions/browser/pref_names.h#72) · [Packed path resolution](https://chromium.googlesource.com/chromium/src/+/refs/tags/158.0.8127.18/extensions/browser/extension_prefs.cc#1649)

## Space and private isolation

| Install | Default | Separate persistent Space | Empty-cache private context |
| --- | --- | --- | --- |
| Launch switch | Active | Active with its own worker and storage. The switch runs for both profiles. | No injection |
| Machine policy | Active after install | Active after its own install and another navigation. The seed ran on the first navigation. | No injection |
| CDP default install | Active | No injection or install record | No injection with the default choice |
| CDP `enableInIncognito: true` | Active | No injection or install record | Script and runtime reply with `incognito: true`. The regular popup could read the value written in the private tab for this spanning extension. |

CEF maps the root to Chrome's default profile, a direct child cache path to a separate persistent profile, and an empty cache path to a unique off-the-record profile of the primary profile. The tests show that install and storage state can be profile-local even when a machine policy or launch flag installs the same ID in every persistent profile. The private context shares extension storage with the regular profile in the tested opt-in spanning mode. Keep that opt-in explicit. Split-mode extensions and the lifecycle after the last private window closes are unverified. ## Recommended route

Start on stock CEF with a clearly scoped unpacked-extension developer mode. Use the launch switch for a launch-time list, or a private browser-level debugging pipe for a dynamic, session-only list in the default Space. Prefer the pipe over exposing a debugging port in the product. Show known popup pages as OSR popovers for extensions that do not need the active tab or a toolbar gesture. Policy is a viable managed-install route. Profile copies alone are a poor installer because provenance controls startup behavior.

If Flecha needs normal Store installs, per-Space choices or Chrome-equivalent actions, maintain a narrow CEF fork. This is the smallest source change set suggested by the traced dependencies. It has not been built:

1. **Expose profile-scoped install and inventory.** Extend CEF `include/cef_request_context.h` and `libcef/browser/request_context_impl.cc` with a browser-process API backed by Chromium `extensions/browser/unpacked_installer.cc`, `extensions/browser/crx_installer.cc` and the profile's `ExtensionRegistry`. Use explicit request context, permission acknowledgement and completion. Return status, resolved popup and icon data from live state. Add a readiness callback based on `extensions/browser/user_script_manager.cc` when first-document injection is required. Regenerate the C API and cef-rs bindings. Preserve Chromium verification and install provenance.
2. **Bridge actions to the GPUI-selected tab.** In CEF `include/cef_browser.h` and `libcef/browser/alloy/alloy_browser_host_impl.cc`, expose a host-only user-action entry point that resolves the extension in the tab's profile and calls Chromium `chrome/browser/extensions/extension_action_runner.cc`. Return the effective per-tab popup URL when the action requests a popup. Preserve the runner's permission and event semantics. Add a CEF-owned tab/window view of GPUI selection in `libcef/browser/alloy/alloy_tab_interface.{h,cc}` and extend Chromium `chrome/browser/extensions/api/tabs/tabs_api.cc` and `chrome/browser/extensions/extension_tab_util.cc` via CEF's `patch/patches/chrome_browser_extensions.patch`. Keep the popup as a separate extension view associated with its opener, with profile and private filtering. Verify `activeTab`, tab events, dynamic popup URLs, and `onClicked` without a popup.
3. **Provide Store confirmation only if Store install is required.** Connect a CEF host callback to Chromium `extensions/browser/api/webstore_private/webstore_private_api.cc` and `chrome/browser/extensions/extension_install_prompt.cc` before the browser-modal Views path. Show the real permission prompt in GPUI and propagate accept and cancel through Chromium's normal install path. A standalone Chrome-style manager window can reuse native confirmation as a separate design option. Alloy tab APIs would still require the action and tab work above. Verify Store availability, permission UX, signed updates and rollback in the packaged application. [Web Store prompt call](https://chromium.googlesource.com/chromium/src/+/refs/tags/158.0.8127.18/extensions/browser/api/webstore_private/webstore_private_api.cc#1162) · [Browser confirmation](https://chromium.googlesource.com/chromium/src/+/refs/tags/158.0.8127.18/chrome/browser/extensions/extension_install_prompt.cc#261)

Maintain the patch set against the pinned Chromium revision and run the isolated matrix at each CEF update.
