# Nightly native build reuse

Nightlies search earlier default-branch runs of `nightly-release.yml` for a compatible portable package or Chromium checkpoint. Failed lookups, downloads, extractions and validation fall back to other candidates or clean preparation. Failed restoration removes only the work directory created for that attempt. The runner cleans up after cancellation. Failed and cancelled nightlies can supply artifacts. Pull requests, forks and other branches cannot.

Only `gh` subprocesses inherit the GitHub token. Source preparation, native build, Git fingerprinting and archive subprocesses receive an environment without GitHub tokens.

Discovery requests GitHub's documented maximum of 100 artifacts per page. One candidate iterator retains fetched pages and run metadata across attempts, so a failed artifact does not restart pagination or repeat trust lookups. API calls, candidate retries, downloads, extraction and configuration share an owner-selected total budget of one hour, configured as `FLECHA_REUSE_BUDGET_MINUTES: '60'`. The existing five-hour stage deadline can shorten that budget. The owner selected one hour to preserve time for a clean preparation and checkpoint handoff within GitHub's six-hour job limit. A failed artifact is excluded from subsequent selection; discovery tries remaining compatible native snapshots and indexed checkpoints before preparing cleanly. Expired allowance stops discovery, and API timeouts fall back without being mistaken for user cancellation.

Native preparation subprocesses run asynchronously with pipes and isolated Unix process groups. At the reuse deadline or cancellation, the runner force-stops the group, using noninteractive sudo for privileged Linux descendants, or uses Windows `taskkill /T /F`. It waits for inherited pipes to close before returning. There is no added termination grace period. If termination fails, preparation stops and preserves the owned tree and download directory instead of starting a competing fallback. Clean preparation awaits the same cancellable runner without the optional reuse deadline, and checks cancellation before starting further work.

On Linux, clean or restored Chromium builds install the system build dependencies. Installation remains cancellable and runs outside the optional reuse deadline so expiry cannot leave dpkg in a broken state. The budget excludes mandatory setup and cleanup and stays within the original five-hour stage deadline. Candidate discovery, transfers and GN configuration use that adjusted deadline.

Failed-tree deletion runs in a cancellable child process with the original stage deadline. Cancellation skips further deletion. If cleanup fails, times out or cannot stop safely, preparation preserves remaining owned files and stops before another attempt or clean build can compete with them. Required cleanup therefore uses the stage allowance, rather than an already-expired optional lookup window.

The SHA-256 compatibility key includes tracked Chromium revision, patches, branding, build configuration and Windows SDK setup; effective GN arguments with a normalized run number; depot_tools revision; source preparation code; platform and absolute workspace path; hosted runner image OS and version; and the selected Xcode or Visual Studio version. Changing a native input or runner image starts a clean build. Shell and packaging changes can reuse compiler outputs.

If hosted image metadata is unavailable, the key includes the current run ID to prevent cross-run reuse.

After restoration, the script checks the previous source SHA, compatibility key, Chromium revision, platform and depot_tools revision. It replaces the staged shell, regenerates GN arguments with the current version and run number, and clears package completion. Restored-tree configuration and GN generation stay inside the guarded reuse attempt and its deadline. Configuration failure discards that owned tree and tries another candidate or prepares cleanly. Ninja then checks the retained native outputs before current-source packaging runs. Package provenance records the current commit and the reused run, artifact and source commit.

Linux and Windows can reuse the browser from a verified `release-<platform>-<key>-<layout>` artifact. The layout fingerprint covers the runtime staging, shell staging and archive commands. A layout change leaves native checkpoints eligible. For each candidate run, discovery tries the portable package before native snapshots and checkpoints. Verification, extraction, and repackaging share the reuse deadline. A failed attempt leaves no partial release and discovery can try another artifact. The new package records the current source, the reused artifact and the arguments that built the browser.

Incomplete stages upload a checkpoint and a small `reuse-<platform>-<key>-<stage>` index. Discovery skips deleted runs and indexes with expired or superseded checkpoints. The final stage keeps its input checkpoint available for retries. Once a package uploads, the stage dispatches `Publish nightly platform` with the artifact ID and build attempt. Later build stages skip. An optional snapshot may save the full Chromium tree on macOS or after a packaging failure. Publication can proceed during that snapshot. A separate Linux job reports the publisher result and cancels an unfinished publisher if the wait fails. Its one-hour allowance is independent of compilation.

Native snapshot creation, native artifact upload and reuse-index upload are optional. Their failure does not block packaging or the required package/checkpoint uploads. The owner selected a separate one-hour upload reserve within the existing five-hour stage allowance, using the six-hour job limit minus the stage allowance as its basis. Snapshot compression stops at the stage deadline minus that reserved hour. If no compression time remains, it skips creating the archive. Compression uses the process-tree runner, and an expired or late result is removed. The native upload step is limited to the whole minutes remaining in the stage allowance. The last incomplete checkpoint is retained after completion, so skipping a full snapshot still permits partial reuse. Cancellation propagates.

Artifacts have a 35-day retention period. A change to the compatibility key still requires a build. Tree reuse still transfers full checkpoints. Portable reuse transfers the previous package and avoids Chromium compilation and checkpoint handoffs. The tests cover compatibility, trusted runs, archive restoration, shell replacement and provenance. Hosted nightlies measure the end-to-end timings.
